- S6. Issue #63 (verbatim title): "Show dialogs in the agent's conversation language, keeping secret names in English". Proposal (verbatim): "1. Render every dialog and window (titles, labels, buttons, help text, warnings, refusal explanations shown to the user) in the language of the agent's conversation. 2. Let the agent pass that language explicitly, for example an optional `locale` field (BCP 47, such as `es-ES` or `en-GB`) on `secret_request`, `secret_manage` and on the unlock or grant prompts that `secret_exec` and `secret_list` can trigger. Fall back to the system locale, then English. 3. Keep identifiers untouched: secret names (`GITHUB_TOKEN`), scopes (`once`, `session`, `project`), layers and machine tokens stay in English in every language, so what the user approves matches what the agent and the audit log name. 4. Update the skill so the agent always sends the conversation language and writes its `reason` in that same language. 5. Ship at least English and Spanish; keep the strings in a catalogue so more languages can be added." Security (verbatim): "The dialog must stay generated by qbit-vault from its own catalogue (the agent picks the language, it never supplies the dialog text) ... Unknown locales fall back safely."
- S7. Issue #64 (verbatim title): "No supported route for long commands: secret_exec is cut at the MCP 60 s timeout and exec requires a session the host never exports". Owner's choice (L2): "Jobs MCP start/status + arreglos de CLI": `secret_exec_start` returns a job id and `secret_exec_status` returns redacted output and the exit code; the job lives in the MCP server process (no daemon). CLI (issue, verbatim): "`exec` accepts project-scoped grants without `--session`"; "the docs and the skill state the effective limit and the supported route for long commands"; comment (verbatim): "Either document the format and how a host obtains its real id, or do not require it when every requested grant is project-scoped."; "resolve the project from the caller's repository (or follow linked worktrees to their main clone), and treat `--cwd` only as the child's working directory. At least say in the error which project layer was searched."
- S8. Issue #62 (verbatim title): "Let agents diagnose rejected credentials without values before asking for a replace". Owner selected all four parts (L2). Proposal (verbatim): "1. **Value-free diagnostics for the agent**, for example a `secret_check` tool (or `secret_list` fields) that answers without returning values: length, and whether a value looks like the declared kind (email, URL, JWT, PEM key…) via an optional `format` metadata field; whether two named secrets hold the same value; whether the value is empty, whitespace-padded, or a common placeholder (`change-me`, `TODO`, `xxx`…). 2. **Skill update** for \"When a service rejects the credential\": before proposing `replace`, run those checks on *every* secret the call used (identifier fields such as emails or usernames too, not only the password), and report what they show. 3. **Replace dialog safety**: warn when the new value equals the current one or another secret in the same layer, and keep the previous value recoverable for a short time (or let the user confirm the old one is discarded), so a replace on a wrong hypothesis does not destroy the only copy. 4. Optional: record the last successful use of a secret (time and command), so the agent can tell \"this worked before\" from \"this never worked\"." Security (verbatim): "The checks return booleans, lengths and format guesses, never values. Equality checks between secrets leak one bit per pair, only for secrets the agent is already granted. Keeping the previous value on replace needs the same at-rest protection as current values and a bounded retention."
