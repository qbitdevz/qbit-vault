# Actionable refusals (issue #60)

Every refusal tells the agent which rule stopped it and what to do instead, in fixed, value-free text, so the agent never loops through unlock, grants or output filters when the cause is something else. Root class from issue #60 (`dump_command` gave no rule and no alternative); fixed for the whole refusal family. The security decisions do not change.

## Specs

- S1. User (verbatim, 2026-11-13): "revisa si el issue que reportaron ya esta solucionado en la ultima version"; then "si, tenemos que solucionar todos estos errores de ejecucion y uso". Issue #60 (verbatim title): "Make dump_command refusals actionable with value-free rule hints"; its acceptance checks (verbatim): "the same unsafe commands remain refused before process creation; safe clients retain their existing behavior; and fake `TESTSECRET_` fixtures never appear in responses or logs."
- S2. Contract (`contracts/secrets-broker/v1/CONTRACT.md` § Refusals, additive and optional, existing consumers unaffected): a refusal MAY carry `"rule": "<fixed id>"` and `"hint": "<fixed text>"`. Both are built only from fixed strings (and, for `hint`, at most the secret name); never a value, the command, an argument, a URL, a path the user typed or a custom pattern's text. `type`, `name`, `retryable` and the exit codes are unchanged.
- S3. `dump_command` gets a `rule` from a closed set and a matching `hint`; its `message` becomes `the command is refused while secrets are injected: <rule phrase>`:
  - `environment_dump` (env, printenv, set, export -p, declare/typeset listing, compgen, `/proc/*/environ`, PowerShell `env:` listing, `[Environment]::GetEnvironmentVariables`, interpreter `-c`/`-e` scripts that read the environment): phrase `it lists or reads the environment`; hint: run the program that needs the secret and let it read its own environment; check presence with `${#NAME}`, never print the environment.
  - `value_print` (echo/printf/Write-Output of `$NAME`, `$env:NAME`, `%NAME%`): phrase `it prints a secret value`; hint: do not print the value; check presence with `${#NAME}`.
  - `value_encode` (base64/xxd/od/hexdump of the value): phrase `it encodes a secret value`; hint: encoding does not hide a value; pass it to the program that needs it through its environment.
  - `network_argument` (curl/wget/http/nc/ncat/socat with the value in an argument): phrase `it puts a secret value in a network command's arguments`; hint: use a client that reads the credential from its own environment variable or config (for example `gh` with `GH_TOKEN`, or a script that reads `os.environ`), or a config file the client loads; filtering the output does not exempt an earlier pipeline segment.
  - `encoded_script` (PowerShell `-EncodedCommand` and its prefixes): phrase `its script is encoded and cannot be checked`; hint: pass the script as plain text.
  - `custom_rule` (a pattern from the user's `dumpguard.yaml`): phrase `it matches a rule in your dumpguard.yaml`; hint: ask the user; the user's own rule is never shown.
  - A fixed, optional `"segment": <n>` (0-based index of the pipeline segment that matched) MAY be added; never the segment text.
  - The default patterns keep their exact behavior: the same commands are refused before any process is created (S1 acceptance). The `dumpguard.yaml` file format does not change (a user file keeps loading); the class of each default pattern lives in code, kept in sync by a test, and every user pattern is `custom_rule`.
- S4. Every other refusal type in the contract table gets a fixed `hint` that names the next action (examples, refine as needed, keep them short): `grant_required` call `secret_request` for the names (and, when a grant exists but does not apply, what to do); `unknown_secret` call `secret_list`, then `secret_request` with `fields` to ask the user to store it; `user_declined` do not ask again for the same use; continue without it or ask the user in the chat; `rate_limited` wait, do not retry the same request; `reason_too_vague` say what the command does and why it needs the secret; `invalid_name` names are `^[A-Z][A-Z0-9_]{0,63}$`; `scope_not_allowed` ask for `once`; `scope_binary` the user must add the program to the secret's binaries; `no_project` use `global` or run from inside the repository; `not_model_callable` this is a user-only action; ask the user to run it; `vault_locked` (keep the 1.4.0 unlock-dialog texts); `vault_corrupt` the user runs `qbit-vault restore`; `timeout` raise `timeout_ms` or split the command; `contract_mismatch` update qbit-vault; `internal` report it with `qbit-vault doctor`.
- S5. Model-facing text: the agent skill (`internal/hosts/skill/SKILL.md`) refusal table uses the rules and hints (and says plainly that an unlocked vault and a valid grant never override the dump guard, and that output filtering is not an exemption); the `secret_exec` MCP tool description mentions the `rule`/`hint` fields; CONTRACT.md documents the fields and the closed `rule` set. The skill test keeps every refusal and rule present.
- S6. Tests (RED first, through the public interface: `qbit-vault exec --json`, the broker/MCP calls, the hook commands where they emit refusals): one test per `rule` with a representative command from the defaults plus the exact refusal JSON; the issue's sanitized pipeline shape (`curl ... -H "Authorization: Bearer $NAME" ... | jq ...`) is refused as `network_argument` with `segment` 0; a user `dumpguard.yaml` pattern is `custom_rule` and its text never appears; every type in S4 returns its hint; the leak battery covers the new fields (no `TESTSECRET_` anywhere); a differential run against v1.4.1 proves the same command set is refused (no command newly allowed or newly refused).
- S7. Docs: CONTRACT.md, AGENT_INTEGRATIONS (refusal section), CLI (exec --json), THREAT_MODEL if it lists refusal content, CHANGELOG `[Unreleased]` → released as 1.5.0 (additive contract field: minor). After release, a comment on #60 drafted for the owner to approve.
